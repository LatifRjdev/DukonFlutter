# Ручное создание пользователя из админ-панели — Design Spec

**Date:** 2026-07-23
**Status:** Approved, ready for implementation planning

## Problem

Сегодня в системе нет способа создать аккаунт пользователя иначе, чем через
самостоятельную регистрацию в мобильном приложении (`POST /api/auth/register`).
Это не покрывает два реальных сценария:

- **Поддержка клиентов**: клиент позвонил/написал в поддержку и попросил
  завести ему аккаунт вручную — сотрудник поддержки создаёт логин и передаёт
  клиенту.
- **QA/тестирование**: нужно быстро создавать тестовые аккаунты для проверки
  функционала, без прохождения обычной регистрации.

Оба сценария одинаково важны и должны обслуживаться одной формой в
существующей веб-админке (`admin/`, раздел `/users`).

## Goals

- Дать администратору (`User.isAdmin = true`) возможность создать нового
  пользователя из панели: имя, телефон, email (опц.), пароль.
- Пароль — на выбор администратора: сгенерировать автоматически (показать
  один раз) или ввести самому.
- Опционально, тем же действием — сразу создать для этого пользователя первый
  магазин (переключатель в форме), переиспользуя существующую логику
  `StoresService.create()` (триал-подписка + роль OWNER создаются
  автоматически, как при обычном онбординге).
- Действие должно попадать в существующий audit log (`AuditInterceptor`),
  как и все остальные admin-мутации.

## Non-goals (явно вне рамок v1)

- Массовое (bulk/CSV) создание пользователей.
- Принудительная смена пароля при первом входе (в системе уже есть
  self-service смена пароля через `/users`/`/auth`, отдельный флаг
  "must change password" не нужен — не будем усложнять схему).
- OTP-верификация телефона при ручном создании (обычная саморегистрация
  `register()` тоже не требует OTP — ручное создание админом остаётся
  на том же уровне доверия).
- Автологин созданного пользователя (в отличие от `register()`, здесь админ
  создаёт аккаунт не для себя — токены не выдаются в ответе).

## Design

### Backend

**Новый эндпоинт**: `POST /admin/users` в
`api/src/modules/admin/admin-users.controller.ts` — использует те же
class-level гварды контроллера (`JwtAuthGuard`, `AdminGuard`) и тот же
`@UseInterceptors(AuditInterceptor)`, что и остальные admin-роуты этого
контроллера. Ничего нового в цепочке авторизации не требуется.

**DTO** (`create-user-by-admin.dto.ts`):
- `name: string` — те же правила, что в `RegisterDto` (`IsSafeText`,
  `MaxLength(80)`).
- `phone: string` — тот же паттерн `+992\d{9}`, что в `RegisterDto`.
- `email?: string` — опционально.
- `password?: string` — опционально. Если передан — валидируется тем же
  `IsStrongPassword`, что при обычной регистрации. Если не передан — сервис
  генерирует случайный пароль той же силы сам.
- `createStore?: boolean` — если `true`, обязательны:
  - `storeName: string`
  - `storeCategory: string` (тот же enum, что в `CreateStoreDto`)
  - `storeCurrency?: string`, `storeAddress?: string`, `storePhone?: string`
    (опционально, как в `CreateStoreDto`)

**`AdminService.createUserManually(dto)`**:
1. Проверить уникальность телефона (`ConflictException`, как в
   `AuthService.register()`).
2. Если `dto.password` не передан — сгенерировать случайный пароль
   (криптографически случайный, той же длины/силы, что требует
   `IsStrongPassword`).
3. Хэшировать пароль (`bcrypt`, 12 раундов — как в `AuthService.register()`).
4. Создать `User` через Prisma (`isAdmin: false` всегда — админ не может
   через эту форму создать другого админа, для этого есть отдельный
   `toggle-admin`).
5. Если `createStore === true` — вызвать существующий
   `StoresService.create(newUser.id, storeDto)` без изменений (переиспользует
   триал-подписку + OWNER-роль "из коробки").
6. Вернуть: данные пользователя (без пароля/хэша), данные магазина (если
   создан), и **пароль в открытом виде — только если он был сгенерирован
   сервером** (если админ ввёл его сам, эхо не нужно — он и так его знает).
   Пароль нигде не сохраняется и не логируется, кроме этого единственного
   ответа.

**Security fix, обязательный для этой задачи**: `AuditInterceptor`
(`api/src/common/interceptors/audit.interceptor.ts`) сейчас пишет
`request.body` в `audit_log.details` без какой-либо фильтрации. Это первый
admin-эндпоинт, в теле запроса которого может быть пароль в открытом виде
(если админ вводит его вручную) — без исправления он попадёт в БД в
audit-логе. Нужно добавить редактирование чувствительных полей (`password`,
и на будущее — любых полей, которые могут появиться, вроде `token`) перед
записью в `details`, заменяя значение на `'[REDACTED]'`. Это точечное
исправление существующего файла, напрямую вызванное этой задачей — тот же
принцип "targeted improvement in the path of the current goal", что
применялся раньше в этой сессии для fix'а notification-settings.

### Frontend (`admin/`)

На странице `/users` — кнопка «+ Создать пользователя», открывает модальное
окно (shadcn `Dialog`, тот же стиль, что у остальных диалогов в панели —
«Продлить», «Передать владение» и т.д.):

- Поля: Имя, Телефон, Email (опц.).
- Пароль: переключатель "Сгенерировать" / "Ввести самому" — при "Ввести
  самому" появляется поле пароля с той же валидацией на клиенте, что и в
  обычной форме регистрации/смены пароля (если такой компонент уже есть в
  коде — переиспользовать).
- Чекбокс «Создать магазин сразу» — при включении раскрывает блок: Название,
  Категория (select с тем же enum), Валюта (опц.), Адрес (опц.).
- После успешного создания:
  - Если пароль был сгенерирован — показать диалог с паролем, кнопкой
    «Скопировать» и предупреждением «Сохраните — этот пароль больше нигде не
    будет показан».
  - Если пароль вводил админ — просто закрыть диалог, показать
    success-toast, обновить список пользователей (React Query invalidate).
- Ошибка "телефон уже занят" — показать инлайн под полем телефона, как
  обычно обрабатываются 409 в этой панели.

## Data integrity

Создание пользователя и (опционально) магазина должно происходить в одной
Prisma-транзакции (`prisma.$transaction`) — если создание магазина упадёт
(например, невалидная категория), пользователь тоже не должен остаться
"осиротевшим" в базе без магазина и без возможности его создать заново тем же
номером телефона (телефон уже будет занят). `StoresService.create()`
принимает `ownerId` уже существующего пользователя, поэтому потребуется либо
передать транзакционный `tx`-клиент в оба вызова, либо создать пользователя и
магазин через прямые Prisma-вызовы внутри одного `$transaction` (решить на
этапе плана, в зависимости от того, насколько легко `StoresService.create()`
принимает внешний `tx`).

## Access control

Как и весь `/admin/*` — доступ только `isAdmin: true`. Отдельной
градации прав внутри админов не вводится (соответствует текущей модели
проекта — плоский булев флаг, без иерархии).
