# Design — Finance Display Correctness + Navigation Polish

**Date:** 2026-05-11
**Scope:** 4 carry-forward bugs from the 2-day session (#26, #28, #29 +
the new "no negative finance numbers" UX request).
**Decisions made (brainstorming Q&A):** C, B, C, B+ii.

## Summary

Four bugs grouped into one focused pass because three of them share a
root cause (`Sale.total` rows can be negative in legacy data, breaking
the finance dashboard aggregation, the sales-history client parser, and
the dashboard's revenue cards). The fourth (#26) is unrelated but
fits the "Финансы / dashboard correctness" theme so it ships in the
same change.

## Bug-by-bug spec

### A — "Общий доход" never goes negative (Q1: option C)

**Problem.** Finance dashboard shows
`Общий доход: -127 TJS`. Conceptually `Общий доход` (revenue) is a
sum of money in — it cannot be negative. The `-127` comes from
legacy `sale.total = -95` rows generated by yesterday's BUG #14
probe.

**Fix layers (3):**

1. **Migration** — set `total = 0`, `subtotal = 0` on any existing
   `sale` rows where they're currently negative. Same for
   `sale_items.total` and `sale_items.discount` (the discount
   was the originator).
2. **DB CHECK constraint** (Q4a: option B) — add
   `CHECK ("total" >= 0 AND "subtotal" >= 0 AND "paidAmount" >= 0
   AND "change" >= 0 AND "debtAmount" >= 0)` on `sales`. Same
   shape on `sale_items` for `total >= 0` and `discount >= 0`.
   Defense in depth — the application clamp from BUG #14 already
   prevents this on the API path, but a future direct SQL admin
   write or broken seed could re-pollute. The constraint blocks
   it forever.
3. **Client tolerance** — even with the data clean, the dashboard
   card display should `Math.max(0, value)` for **only the
   sums-of-money-flowing fields**: "Общий доход" and "Общие
   расходы". These are aggregates of strictly non-negative inputs
   and cannot be negative conceptually.
   - "Валовая прибыль" (= Общий доход − Себестоимость) **stays
     as-is including negatives**. If the merchant sells products
     for less than they cost (cost=5, sold=4 → -1), this IS a
     legitimate signal they should see, not a number to hide.
   - "Чистая прибыль" (= Валовая − Расходы) likewise keeps
     negatives — a loss is a real, important number for the
     merchant.
   - Color stays red on any negative. The `-` prefix appears only
     when the value is genuinely negative on profitability cards;
     the two revenue cards never show `-`.

**Acceptance.**
- After migration, no `sale.total < 0` row exists in any environment.
- DB rejects any new write with `total < 0` (verified by failing
  e2e test that tries to bypass the API).
- Финансы dashboard:
  - Общий доход shows `0 TJS` minimum (never `-X TJS`).
  - Общие расходы shows `0 TJS` minimum (never `-X TJS`).
  - Валовая прибыль = `Общий доход − Себестоимость`. Can be
    negative if cost > revenue; if so, shows `-X TJS` in red.
  - Чистая прибыль = `Валовая прибыль − Расходы`. Same — can be
    negative; if so, shows `-X TJS` in red.
  - The two revenue cards never show `-`; the two profitability
    cards may legitimately show `-` when the merchant operates
    at a loss.

### B — "Остатки на складе" tile pre-filters Товары (Q2: option B)

**Problem.** Dashboard tile says "Остатки на складе / 11 товаров"
but tapping it lands on the unfiltered Товары tab. Merchant
expects the stock-attention view (low/out-of-stock).

**Fix.** Tile navigation passes a query param / route state that
opens the Товары tab with the filter chip pre-set to
`Заканчивается + Нет в наличии` (the union of attention-needed
states). Merchant lands on exactly the rows requiring action.

**Implementation note.** ProductListPage already has filter chips
("Все / В наличии / Заканчивается / Нет в наличии"). We need to
extend the chip model to accept a multi-select state for the new
"requires attention" preset (Заканчивается ∪ Нет в наличии) — OR
introduce a single "Требует внимания" chip that's the union, and
pre-select it. The latter is simpler and doesn't disturb existing
single-select logic. Recommend the new chip.

**Acceptance.**
- Tap "Остатки на складе" tile → lands on Товары tab with
  "Требует внимания" chip pre-selected.
- The list shows only products in `Заканчивается` or `Нет в наличии`
  state.
- Tapping any other chip (Все / В наличии / Заканчивается /
  Нет в наличии) deselects "Требует внимания" and applies the
  tapped chip — single-select semantics, no multi-select state.
- Tapping "Требует внимания" itself again does nothing (already
  selected); tapping it from another chip selects it.
- Direct navigation to Товары tab via bottom-nav button still
  defaults to "Все" (no breakage).

### C — История продаж parser resilience + root-cause fix (Q3: option C)

**Problem.** Ещё → История продаж always shows
"Не удалось выполнить операцию" even though the API returns 200 OK
with valid sales data. Suspected client-side `Sale` model parser
choking on a row.

**Fix layers (2):**

1. **Root cause** — once the negative-totals migration from A.1 lands,
   re-test. If error remains, add Dio response logging in dev mode
   for `/sales` and inspect the failing field. Likely candidates:
   - `null` in a field the parser expects non-null.
   - `customer` object structure mismatch.
   - Decimal formatting (string vs number).
   - The new `localId` / `occurredAt` / `syncedAt` fields the API
     emits but the client model may not handle.
2. **Parser resilience** — wrap each row's parse in
   try/catch. On failure: log warning to logger + Sentry,
   skip the row, continue with the rest. Page renders the rows
   that DID parse, with a small "1 запись пропущена" footer
   if any failed. Beats blanking the whole page.

**Acceptance.**
- After migration, История продаж renders all 23 sales without
  errors.
- If a future malformed row appears in the response, it's silently
  skipped (logged) and the rest of the list still renders.
- Spec test: feed parser a mixed-list payload (1 valid, 1 missing
  required field, 1 valid) → expect 2 sales rendered + 1 warning
  log entry.

### D — Orphan debt cleanup (Q4b: option ii)

**Problem.** `Sale` rows with `customerId IS NULL AND debtAmount > 0`
are orphan debts — money the merchant is technically owed by no one
(the F4.1 fix prevents this going forward, but legacy rows from
before F4.1 may exist).

**Fix.** Migration that sets `debtAmount = 0` on those orphan rows
(the merchant cannot collect; clearing the debt simply removes the
phantom). Log how many rows were touched in the migration's STDOUT
so the operator knows the impact.

**Acceptance.**
- Post-migration, no row matches
  `customerId IS NULL AND debtAmount > 0`.
- A second migration run is a no-op (idempotent).

## Architecture / files touched

**API (NestJS)**
- `prisma/migrations/<NEW>_finance_correctness/migration.sql`:
  - UPDATE sales SET … WHERE total < 0 OR subtotal < 0 OR …
  - UPDATE sale_items SET … WHERE total < 0 OR discount < 0
  - UPDATE sales SET debtAmount = 0
    WHERE "customerId" IS NULL AND "debtAmount" > 0
  - ALTER TABLE sales ADD CONSTRAINT … CHECK …
  - ALTER TABLE sale_items ADD CONSTRAINT … CHECK …
- No service-code changes (the API clamp from BUG #14 already
  handles new writes correctly).

**App (Flutter)**
- `lib/presentation/pages/dashboard/dashboard_page.dart` — pass
  filter preset to Товары when tapping "Остатки на складе" tile.
- `lib/presentation/pages/product/product_list_page.dart` — accept
  preset filter param; add "Требует внимания" chip option.
- `lib/presentation/pages/finance/finance_dashboard_page.dart` —
  clamp negative display values for `Общий доход`, `Общие расходы`,
  `Валовая прибыль`. Keep `Чистая прибыль` as-is.
- `lib/data/datasources/remote/sale_remote_datasource.dart` (or
  wherever `_mapSale` lives) — wrap per-row parse in try/catch,
  warn-and-skip on failure.
- `lib/presentation/pages/sales/sales_history_page.dart` — show
  "X rows skipped" footer when any rows are dropped.

**Tests**
- API: e2e test that posts SQL `INSERT INTO sales (total, …) VALUES
  (-1, …)` (or via raw Prisma `$executeRaw`) → expect Postgres
  rejection. Validates the CHECK constraint.
- App: parser test that feeds a mixed-list (valid + malformed +
  valid) → expect 2 entries + 1 warn log.
- App: dashboard widget test asserting display clamps for the 3
  always-positive fields and preserves negative for `Чистая
  прибыль`.

## Roll-out order

1. Migration goes first (idempotent — safe to run on prod).
2. Service is unchanged so API tests still pass with no spec edits.
3. Flutter changes ship in a single APK.
4. After deploy, manual verification:
   - Open Финансы → assert all-positive display except possibly
     Чистая прибыль.
   - Open Главная → tap "Остатки на складе" → land on Товары with
     "Требует внимания" preset.
   - Open Ещё → История продаж → list renders.

## Risks

- **CHECK constraint migration** could fail if production has rows
  we didn't anticipate. Mitigation: the UPDATE statements run
  BEFORE the ALTER TABLE, so the constraint will only fail if the
  cleanup query missed a case. We grep the schema for all numeric
  decimal columns on `sales` and constrain only the ones that are
  conceptually non-negative.
- **Filter preset** could surprise users who expected the old
  behaviour. Mitigation: tile label change is unnecessary because
  "Остатки на складе" reads as "what's on the shelf needing
  attention" in Russian — a closer match to the new behaviour
  than the old.
- **Parser resilience** silently swallowing rows could mask real
  issues. Mitigation: each skipped row logs a Sentry breadcrumb
  with the bad field; a counter in the UI footer tells the user
  something was dropped. They'll notice.
