# Отчёт по прогону ручного теста — 2026-09-07

Прогон по `qa/2026-09-05-manual-test-plan/PLAN.md`. Тестировалось живьём на
Android-эмуляторе (Android 16 / API 36) против локального dev API
(`http://10.0.2.2:4455/api`), сборка debug APK из текущего `main`.

Методология тапов: координаты элементов берутся через
`adb shell uiautomator dump` (реальные `bounds` из accessibility-дерева),
а не визуальной оценкой по скриншоту — визуальная оценка на скриншотах
ранее приводила к ложным промахам мимо цели.

## Окружение

- Первая попытка (emulator-5554, исходный запуск) уткнулась в нехватку
  памяти хоста (~70МБ свободно) — тапы перестали доходить до приложения
  примерно на середине раздела 2. Эмулятор перезапущен холодным стартом
  (`-no-snapshot-load`), после чего память хоста восстановилась
  (~176МБ свободно сразу после убийства старого процесса) и тестирование
  продолжено успешно.

### 🟡 Новая находка: форма "Редактировать/Добавить магазин" — нет валидации и форма закрывается до ответа сервера

**Как воспроизвести:** "Мои магазины" → карандаш на карточке магазина →
очистить поле "Название" → "Сохранить".

**Фактическое поведение:** нижний лист **сразу закрывается**, а через
секунду появляется общий красный снекбар "Не удалось выполнить
операцию" — без указания, что именно не так и с какими полями.
Название магазина в списке не изменилось (сервер, судя по всему,
отклонил пустое название 400-м, что хорошо), но пользователь не
понимает причину и теряет уже введённые (в данном случае прочие пустые)
поля формы.

**Причина (подтверждено чтением кода,
`lib/presentation/pages/settings/my_stores_page.dart`):**
- `_showStoreForm` (строка 65) использует обычные `TextField` без
  `Form`/`TextFormField`/`validator` — в отличие от отдельного экрана
  онбординга `create_store_page.dart` (который открывается сразу после
  регистрации и, судя по коду, имеет нормальную валидацию — см. раздел
  2.1). Это **два разных места создания магазина** с разной логикой:
  онбординг-экран и кнопка "+"/карандаш на "Мои магазины".
- Кнопка "Сохранить"/"Создать" (строка 137) делает
  `Navigator.pop(ctx)` **безусловно и синхронно, до** вызова `await
  _saveStore(...)` — то есть лист закрывается независимо от того,
  успешен запрос или нет. `_saveStore` (строка 157) в случае ошибки
  просто показывает `AppSnackbar.error(context,
  mapErrorToUserMessage(e))` — общий текст с сервера, не привязанный к
  конкретному полю.
- Итог: **любая** ошибка сохранения на этой форме (не только пустое
  название — то же будет при обрыве сети, дублирующемся названии и
  т.п.) выглядит одинаково — форма закрывается, пользователь видит
  неинформативный тост и должен заново открывать форму и вспоминать,
  что вводил.

**Серьёзность:** средняя — не блокирует основной сценарий (у формы
онбординга валидация есть), но ухудшает UX редактирования существующих
магазинов и создание дополнительных магазинов через "Мои магазины" →
"+". Специфично для этого конкретного файла/формы, не системная
проблема.

**Исправлено:** коммит `9d4bc46`
(`fix(mobile): validate store name and stop discarding edits on save
error`). Поля обёрнуты в `Form` с валидатором "Введите название" на
обязательном поле "Название" (плюс звёздочка на метке, как у
"Категория \*"), а `Navigator.pop(ctx)` теперь вызывается **только**
при успешном сохранении — при ошибке (сетевой, валидационной с
бэкенда и т.п.) лист остаётся открытым с уже введёнными данными и
снекбаром ошибки, а не закрывается вслепую. Добавлены тесты
взаимодействия на три пути (клиентская блокировка, ошибка сервера —
лист остаётся открытым, успех — лист закрывается), проверено методом
break-then-fix.

**Подтверждено живьём на эмуляторе** (2026-09-21): "Мои магазины" →
карандаш → очистить "Название" → инлайн-ошибка "Введите название"
появляется автоматически при потере валидности (без отправки на
сервер), лист остаётся открытым; ввод названия обратно — ошибка
автоматически пропадает (совместно с фиксом `3b5e0fc` для
`AppTextField`).

### 🟡 Новая находка: переполнение (overflow) карточки профиля в хабе настроек при длинном имени+фамилии

**Как воспроизвести:** Настройки → Профиль → заполнить "Фамилия" →
"Сохранить" → вернуться на хаб "Настройки".

**Фактическое поведение:** карточка профиля на хабе "Настройки"
показывает debug-баннер Flutter "RIGHT OVERFLOWED BY 16 PIXELS"
(жёлто-чёрная штриховка) поверх бейджа роли — текст `"Test_Owner
TestSurname"` вместе с бейджем "Владелец" не помещается в строку и
вылезает за пределы карточки.

**Причина (подтверждено чтением кода,
`lib/presentation/pages/settings/settings_page.dart:292-311`):**
внутренний `Row` (Имя + бейдж роли) находится внутри `Expanded`, но сам
`Text(user.name, ...)` **не обёрнут** в `Flexible`/`Expanded` с
`overflow: TextOverflow.ellipsis` — при достаточно длинном
`user.name` (имя + фамилия) он рендерится в полную длину и толкает
бейдж роли за границу карточки, вместо того чтобы обрезаться
многоточием.

**Серьёзность:** низкая/средняя — чисто визуальный дефект (только в
debug-сборке виден явный красно-жёлтый оверлей; в release он обычно
проявляется как обрезанный/наехавший друг на друга контент без
диагностического баннера), не блокирует функциональность, но ухудшает
вид хаба настроек для пользователей с длинными именем+фамилией.

**Не исправлено в рамках этого тестового прогона** — только
задокументировано.

### 🔴 Находка: после сохранения редактирования сотрудника экран "Профиль сотрудника" остаётся пустым

**Как воспроизвести:** "Сотрудники" → тап по карточке → "Профиль
сотрудника" → иконка редактирования → изменить что-либо (или не
менять) → "Сохранить".

**Фактическое поведение:** снекбар "Сотрудник обновлён" показывается
корректно, но после возврата на экран "Профиль сотрудника" **весь
контент экрана (аватар, имя, роль, телефон, вкладки Смены/
Статистика) пропадает** — остаётся только пустой AppBar с заголовком
"Профиль сотрудника" и кнопкой "Назад" **без иконки редактирования**.
Состояние не самовосстанавливается — подтверждено ожиданием (не
временный лоадер).

**Корневая причина (подтверждено чтением кода):**
- `staff_detail_page.dart`, `body: BlocBuilder<StaffBloc, StaffState>`
  обрабатывает только `StaffLoading`/`StaffError`/`StaffDetailLoaded`
  — для любого другого состояния `StaffBloc` рендерится пусто (нет
  `else`-ветки с фолбэком).
- `add_staff_page.dart`, обработчик успеха формы
  (`StaffFormSuccess`) **всегда** диспатчит `LoadStaff(storeId:
  ...)` — событие, которое обновляет **список** сотрудников
  (`StaffBloc._onLoadStaff` → `emit(StaffLoaded(...))`), — а не
  `LoadStaffDetail`, которое обновляет **детальную карточку**
  (`_onLoadStaffDetail` → `emit(StaffDetailLoaded(...))`).
- Поскольку `AddStaffPage` и `StaffDetailPage` используют **один и
  тот же** экземпляр `StaffBloc` (общий provider выше по дереву), а не
  отдельные scoped-блоки, `LoadStaff` после успешного сохранения
  **подменяет** состояние с `StaffDetailLoaded` на `StaffLoaded` ещё
  до того, как `context.pop()` вернёт пользователя на экран деталей —
  и `BlocBuilder` детального экрана перестаёт находить подходящую
  ветку `if`.
- В самом `StaffBloc` уже ЕСТЬ правильный ивент `LoadStaffDetail`
  специально для этого случая — просто `add_staff_page.dart` его не
  использует при `_isEditing == true`.

**Серьёзность:** высокая — путь "открыл сотрудника → отредактировал →
вернулся" (вероятно, самый частый сценарий использования этого
экрана) оставляет пользователя на полностью пустом, тупиковом экране;
требуется ручной "Назад" и повторный вход в карточку, чтобы увидеть
актуальные данные. Тот же архитектурный паттерн (общий bloc,
list-reload после действия на detail-экране), что уже был
исправлен в прошлом для Долгов/Клиентов/Поставщиков (пост-план
находка №1) — здесь регрессировал в отдельном модуле (Сотрудники),
не покрытом тем прошлым фиксом.

**Исправлено:** коммит `695d3ab`
(`fix(mobile): fix blank Профиль сотрудника screen after editing`).
`StaffBloc` уже содержал правильный ивент `LoadStaffDetail` именно для
этого случая — `add_staff_page.dart` теперь диспатчит его при
`_isEditing == true` вместо `LoadStaff`, сохраняя `LoadStaff` только
для сценария создания (который возвращает на экран списка). Добавлен
регресс-тест с настоящим `GoRouter` (по образцу уже существующего
`debts_overview_reload_test.dart` для того же класса бага), проверено
методом break-then-fix.

## Раздел 10.2: Роли и права

### 🔴 КРИТИЧНАЯ находка (регресс находки №4): сохранение прав роли падает с "Некорректные данные" почти для всех переключателей

**Как воспроизвести:** "Ещё" → "Роли и права" → вкладка "Админ" →
включить переключатель "Продажи" → "Сохранить".

**Фактическое поведение:** запрос падает, снекбар "Некорректные
данные", и **весь список разрешений на экране пропадает**, заменяясь
одной строкой текста "Некорректные данные" по центру экрана — не только
тост, но и разрушение содержимого экрана (нужно выйти и зайти заново,
чтобы увидеть список опять). Возврат назад и повторный вход показывает,
что изменение **не сохранилось** (как и ожидалось при ошибке), но сам
факт критичен: **практически ни один переключатель, кроме 4 из 14, в
принципе не может быть сохранён**.

**Корневая причина (подтверждено чтением кода) — рассинхронизация
списков разрешений между мобильным приложением и backend:**

- Мобильное приложение
  (`lib/presentation/pages/roles/roles_page.dart:44-59`,
  `_allPermissions`) оперирует 14 ключами: `manage_products,
  manage_sales, manage_returns, view_reports, manage_staff,
  manage_expenses, manage_customers, manage_suppliers, manage_stock,
  manage_debts, manage_settings, open_close_shift, apply_discounts,
  manage_payroll`.
- Backend (`api/src/modules/roles/roles.service.ts:6-17`,
  `ALL_PERMISSIONS`) знает только 10 **других** ключей: `view_sales,
  create_sales, cancel_sales, view_profit, change_prices,
  manage_products, add_expenses, manage_customers, manage_staff,
  view_reports`.
- Пересекаются только 4 ключа: `manage_products`, `manage_staff`,
  `manage_customers`, `view_reports`. Остальные 10 ключей мобильного
  приложения (`manage_sales`, `manage_returns`, `manage_expenses`,
  `manage_suppliers`, `manage_stock`, `manage_debts`,
  `manage_settings`, `open_close_shift`, `apply_discounts`,
  `manage_payroll`) backend вообще не распознаёт.
- `RolesService.updatePermissions` (строки 127-132) явно проверяет
  ключи через `ALL_PERMISSIONS.includes(p)` и бросает
  `BadRequestException('Invalid permissions: ...')`, если хоть один
  ключ из присланного `dto.permissions` не входит в список — а
  клиент **всегда** отправляет полный набор из 14 ключей разом
  (`rolePermission.permissions` — вся карта состояния вкладки, не
  только изменённый тумблер), поэтому **любое** сохранение с
  вкладки Админ/Кассир/Складовщик обречено на 400, если в текущем
  состоянии присутствует хоть один из несовпадающих 10 ключей — что
  практически гарантировано, так как именно они формируют
  большинство переключателей на экране.
- Также похоже, что и **набор самих прав рассинхронизирован по
  смыслу**, не только по именам (например, у backend есть
  `cancel_sales`/`view_profit`/`change_prices`, которых нет в
  мобильном списке вообще, и наоборот `manage_stock`/`manage_debts`/
  `manage_payroll` есть только на мобильном) — то есть это не опечатка
  в одном ключе, а полноценное расхождение схемы прав между клиентом
  и сервером, вероятно возникшее при независимых доработках staff/roles
  модуля на бэкенде и мобильном фронтенде в разное время.

**Серьёзность:** критичная — это прямой регресс уже закрытой ранее
находки №4 ("переключатель разрешения реально сохраняется на
сервере"), и затрагивает саму основу ролевой модели доступа
(RBAC) — Владелец не может ограничить/расширить права
Админа/Кассира/Складовщика почти ни по одному значимому пункту
(товары, продажи, возвраты, расходы, поставщики, склад, долги,
настройки, смены, скидки, зарплата), а только по 4 из 14. Это
системная проблема, а не отдельный edge-case, и напрямую подрывает
безопасность и управляемость доступа для любого магазина с более чем
одним сотрудником.

**Дополнительно:** экран разрушает список прав целиком при ЛЮБОЙ
ошибке сохранения (см. `roles_page.dart` — вероятно, состояние ошибки
из `RolesBloc` подменяет `RolesLoaded` без сохранения
`_lastLoadedRoles`/`_hasLoadedOnce` для этого пути), а не просто
показывает снекбар поверх уже отрисованного списка — стоит
перепроверить при исправлении.

**Исправлено:** коммит `87de6ae`
(`fix(api): accept the mobile app's full permission key set on role
save`). По решению пользователя реализован **минимальный** объём
исправления — расширен whitelist (`ALL_PERMISSIONS`) и дефолтные
значения (`DEFAULT_PERMISSIONS`) на backend
(`api/src/modules/roles/roles.service.ts`) до объединения списков
(14 ключей мобильного приложения + оставшиеся уникальные из старых
10). Это устраняет ошибку сохранения для всех 14 переключателей.
**Важная оговорка, зафиксированная в коде и здесь**: часть ключей
(как несколько уже существовавших раньше — `view_sales`,
`view_profit`, `change_prices`, так и часть новых) по-прежнему **не
подключены к реальной проверке доступа** на бэкенде (см.
`api/src/common/guards/permissions-matrix.ts` и его
`LEGACY_PERMISSION_ALIASES`) — то есть переключатель сохраняется, но
не обязательно реально на что-то влияет для части пунктов. Это
осознанно оставлено как отдельная, более крупная задача (полноценный
аудит и подключение прав к реальным guard'ам), а не часть этого
минимального фикса. Добавлен регресс-тест
(`roles.service.spec.ts`), проверено методом break-then-fix (без
фикса тест падает с той же ошибкой `BadRequestException: Invalid
permissions: manage_sales, ...`, что и живьём), полный набор тестов
модуля — 11/11 зелёных, `tsc --noEmit` — чисто.

**Подтверждено живьём на эмуляторе** (2026-09-14): backend
пересобран и перезапущен с фиксом. "Роли и права" → "Админ" →
включить "Продажи" → "Сохранить" → снекбар "Настройки сохранены" (не
"Некорректные данные"), список разрешений остался на экране (не
разрушился). Выход с экрана и повторный вход на вкладку "Админ" —
переключатель "Продажи" остался включённым, изменение реально
сохранилось на сервере.

### 🟡 Минорная находка: текст ошибки "Сумма не может превышать" не пропадает при исправлении значения

**Как воспроизвести:** "Принять оплату" → ввести сумму больше
максимума (появляется ошибка) → изменить сумму на валидную (≤
максимума), не закрывая диалог.

**Фактическое поведение:** текст ошибки "Сумма не может превышать
N.NN" и красная рамка поля **остаются видны** даже после того, как
введённое значение снова становится валидным — обновляются только
после повторного открытия диалога. Само нажатие "Принять оплату" при
этом проходит успешно с корректной (валидной) суммой — то есть это
чисто визуальный лаг, не блокирующий функциональность.

**Серьёзность:** низкая — вводит пользователя в заблуждение визуально
(кажется, что форма всё ещё невалидна), но не мешает оформить платёж.

**Исправлено:** коммит `3b5e0fc`
(`fix(mobile): re-validate AppTextField as the user types after a
failed submit`). Корневая причина — общий виджет `AppTextField`
(`lib/presentation/widgets/common/app_text_field.dart`, использует
его и `payment_form.dart`) не задавал `autovalidateMode`, поэтому
Flutter'овский `TextFormField` по умолчанию перепроверяет валидатор
только по явному вызову `Form.validate()`, а не при каждом изменении
текста. Добавлен `autovalidateMode:
AutovalidateMode.onUserInteraction` — теперь поле перепроверяется
само по себе после первой неудачной попытки сохранения. Это разовое
исправление на уровне общего виджета автоматически чинит **оба**
задокументированных случая с "зависшим" текстом ошибки в этом
прогоне (эта находка и находка ниже про "Имя инвестора"). Добавлен
юнит-тест виджета, проверено методом break-then-fix.

причины** (истёкшая подписка, 400, 404, отсутствие сети, 500 и т.д.).
Для причин вроде истёкшей подписки это особенно вводит в

приложения — см. раздел 17.2 плана, где для интернет-магазина есть
отдельный диалог апсейла).

**Корневая причина (подтверждено чтением кода):**
`lib/presentation/pages/finance/reports_page.dart` (`_loadSales`,
`_loadExpenses`, `_loadProfit` и др., строки ~268-430) делает
HTTP-запросы **напрямую через сырой `Dio`** (`_dio.get(...)`), в
обход стандартного слоя нормализации ошибок, который используют
datasource-классы в остальном приложении (`_handleDioError` →
`ServerException(statusCode: ...)`). Пойманное исключение — сырой
`DioException`, а не `ServerException`, поэтому общая функция
`mapErrorToUserMessage` (`lib/core/errors/error_messages.dart`) не
может определить код ответа (400/403/404/500) и **всегда** попадает
в самую последнюю ветку "неизвестный тип исключения" →
"Не удалось выполнить операцию", вместо специфичных сообщений
("Недостаточно прав" для 403 и т.д.), которые работают на других
экранах, использующих правильный слой.

**Серьёзность:** средняя — не блокирует работу приложения в целом
(это единственный экран с таким паттерном из всех проверенных в этом
прогоне), но ухудшает диагностируемость сбоев именно там, где отчёты
особенно нужны владельцу магазина, и создаёт "мёртвую петлю" retry
для невосстановимых ошибок вроде истёкшей подписки.

**Не исправлено в рамках этого тестового прогона** — только
задокументировано.

### 🔴 КРИТИЧНАЯ находка: «История продаж» всегда пустая, независимо от реальных данных — **[ИСПРАВЛЕНО: 27fc2c1]**

что сервер вернул данные.

**Корневая причина (найдена чтением кода):**
- Backend, list-эндпоинт `GET /stores/:id/sales`
  (`api/src/modules/sales/sales.service.ts`, метод `findAll`) намеренно
  возвращает **облегчённую** проекцию `items`: только `{id, productName,
  quantity, total}` (вероятно, для производительности пагинированного
  списка) — без `saleId`, `productId`, `unitPrice`.
- Мобильный клиент (`sale_remote_datasource.dart`, метод
  `_mapSaleItem`) написан в расчёте на **полную** форму item (как в
  detail-эндпоинте `findOne`) и делает `json['productId'] as String`,
  `json['saleId'] as String`, `(json['unitPrice'] as num).toDouble()`
  **без `?`** — жёсткие приведения без учёта null.
- В логах подтверждена реальная ошибка при парсинге:
  `SaleRemoteDatasource: skipped malformed row: type 'Null' is not a
  subtype of type 'String' in type cast`, стек ведёт прямо в
  `_mapSaleItem` (`sale_remote_datasource.dart:175`).
- `getSales()` оборачивает разбор **каждой продажи целиком** в try/catch
  (комментарий в коде — "BUG #28", уже была похожая проблема раньше) —
  но поскольку `_mapSaleItem` бросает исключение **внутри** `_mapSale`
  при разборе позиций, весь объект продажи считается "повреждённой
  строкой" и тихо пропускается (`skippedRows++`), хотя на самом деле
  продажа полностью валидна — просто её товарные позиции пришли в
  укороченной форме. **Из-за этого абсолютно ВСЕ продажи в списке
  постоянно пропускаются, и список всегда пуст**, а `total`/`totalPages`
  (пришедшие из отдельного `count()`-запроса на backend) остаются
  корректными — отсюда несовпадение: заголовок дашборда правильно
  показывает "1 продаж", а сам список продаж — пустой.

**Серьёзность:** критичная — экран "История продаж" полностью
нефункционален для просмотра списка (хотя карточка транзакции при
переходе по прямой ссылке, видимо, работает через detail-эндпоинт
`findOne`, у которого форма items полная). Это системная проблема,
блокирующая одну из основных функций приложения для ВСЕХ пользователей
и ВСЕХ продаж, а не отдельный edge-case.

**Рекомендация (не реализовывалась в рамках этого тестового прогона):**
либо ослабить `_mapSaleItem` на клиенте (сделать `productId`/`saleId`/
`unitPrice` опциональными для list-контекста, взяв `saleId` из
родительского `sale.id`), либо расширить проекцию `items` в
`sales.service.ts findAll`, либо завести отдельный
"облегчённый" DTO/маппер специально для списка. Также стоит убрать
"проглатывание" ошибки на уровне целой продажи — сейчас баг в разборе
ОДНОЙ позиции тихо прячет ВСЮ продажу из списка без какого-либо
индикатора для пользователя (`skippedRows` есть в состоянии блока, но
не отображается в UI — не проверено отдельно, стоит перепроверить).

**Исправлено:** коммит `27fc2c1`
(`fix(mobile): parse sales-list items using the lightweight backend
projection`). Реализован первый вариант из рекомендации выше —
`_mapSaleItem` в `sale_remote_datasource.dart` теперь принимает
`parentSaleId` от `_mapSale` и делает `productId`/`saleId`/`unitPrice`
опциональными с производными фолбэками (`saleId` ← `parentSaleId`,

### 🔴 Новая находка: "Себестоимость" на Дашборде всегда 0, "Прибыль" не учитывает COGS

**Как воспроизвести:** создать товар с себестоимостью 50 и ценой продажи
80, продать 2 шт наличными (итого 160 TJS выручки). Дашборд показывает
"Прибыль: 160 TJS" и "Себестоимость: 0 TJS" — оба значения неверны:
ожидалось бы "Себестоимость: 100 TJS" (2×50) и "Прибыль: 60 TJS"
(160−100), если бы прибыль считалась с учётом себестоимости проданного
товара.

**Причина (подтверждено чтением кода):**
- Мобильное приложение (`dashboard_remote_datasource.dart:50`) читает
  поле `todayCost` с фолбэком на `costOfGoods` из ответа
  `/finances/overview`, по умолчанию `0`, если ни одного из полей нет.
- Backend (`api/src/modules/finances/finances.service.ts`, метод
  формирования overview) **вообще не вычисляет и не возвращает** ни
  `todayCost`, ни `costOfGoods` — grep по всему файлу не находит этих
  полей. Поэтому мобильный фолбэк на `0` срабатывает всегда, безусловно.
- "Прибыль" в этом же файле (`const profit = totalRevenue -
  totalExpenses;`) считается как выручка минус операционные расходы
  (`Expense`), **без вычета себестоимости проданных товаров** —
  архитектурно это, видимо, осознанное решение (валовая прибыль минус
  расходы, а не чистая прибыль с учётом COGS), но в сочетании с вечным
  нулём в "Себестоимость" создаёт у пользователя ложное впечатление
  "прибыль = вся выручка", что может быть некорректно для бизнес-решений
  о ценообразовании.

**Серьёзность:** высокая — это ключевая финансовая метрика на главном
экране, которую видит владелец магазина каждый день. Требует решения
продукта: либо реализовать реальный расчёт COGS на backend, либо (если
"Себестоимость" не планируется — убрать это поле из мобильного UI, а не
показывать обманчивый ноль.

**Не исправлено в рамках этого тестового прогона** — только
задокументировано согласно задаче "тестировать, а не чинить".

### 🔴 КРИТИЧНАЯ находка (ИСПРАВЛЕНО): кнопка "Открыть смену" не отображается — весь флоу открытия смены недоступен в UI

**Как воспроизвести:** "Ещё" → "Смены" (без открытой смены) → экран
"Нет смен".

**Фактическое поведение:** кнопки "Открыть смену" нет нигде на
экране — ни в шапке, ни в пустом состоянии, несмотря на то, что текст
подсказки прямо говорит "Откройте смену, чтобы начать приём
платежей". `OpenShiftPage` полностью реализован и подключён к роутеру
(`/shifts/open`), а в `shifts_page.dart` уже есть готовый условный
`OutlinedButton` в шапке (`if (state is ShiftLoaded && state.currentShift
== null)`) с правильным `onPressed`, — но эта кнопка никогда не
появляется на экране, при этом никакого видимого краша или ошибки
нет, остальной экран рендерится нормально.

**Корневая причина (подтверждено через `flutter run` с живым выводом
консоли — статичное чтение кода и обычный виджет-тест НЕ
воспроизвели проблему):** рендер этой кнопки бросает исключение
Flutter-рендерера `"BoxConstraints forces an infinite width"`
(`shifts_page.dart:124`, `OutlinedButton` размещён прямо в `Row` рядом
с `Spacer()`). Flutter перехватывает исключение на уровне рендер-слоя
без падения всего приложения — кнопка просто никогда не отрисовывается
и не показывает никакой видимой ошибки, что делает баг крайне сложным
для диагностики визуально или по логам приложения (только `flutter
run` с полным выводом консоли показал полный стектрейс).

**Серьёзность:** критическая — единственный способ открыть смену в
приложении был полностью недоступен, что блокировало весь раздел 12
плана (12.1, 12.2, 12.3 не тестировались до этого исправления).

**Исправлено:** коммит `77b54b0`
(`fix(mobile): "Открыть смену" button invisible due to unbounded-width
layout error`). Кнопка обёрнута в `IntrinsicWidth`, что даёт ей
конечную ширину вместо наследования неограниченной ширины от `Row`.
Добавлен `shifts_page_open_button_test.dart` для базового покрытия
(рендер без исключений, тап переходит на `/shifts/open`) — явно
отмечено в коде, что этот тест **не воспроизводит сам баг** (проходит
и с фиксом, и без него), так как проблема — в реальном рендер-пайплайне
устройства, а не в виджет-тест-харнессе; единственной надёжной
проверкой стала живая верификация на эмуляторе.

**Подтверждено живьём на эмуляторе** (2026-09-21): кнопка "Открыть
смену" отображается в шапке экрана "Смены", открывает форму, форма
успешно открывает смену.

### 🔴 КРИТИЧНАЯ находка (ИСПРАВЛЕНО): Z-отчёт всегда падает с "Не удалось выполнить операцию", хотя запрос к серверу успешен

**Как воспроизвести:** открыть смену → закрыть смену (сумма
наличных) → приложение автоматически переходит на экран "Z-отчёт".

**Фактическое поведение:** экран показывает "Не удалось выполнить
операцию" красным баннером, при этом сетевой запрос `GET
/shifts/:id/z-report` в логах завершается **200 OK** с корректным
телом ответа — то есть сбой происходит не в сети, а при разборе
(парсинге) уже полученных данных на клиенте.

**Корневая причина (подтверждено чтением кода и логов сети):**
`ZReport.fromJson` был написан в расчёте на плоскую JSON-структуру
(`staffName`, `openedAt`, `cashTotal`, `openingCash`, `actualCash`,
`difference`, строковое поле `duration`, `topProducts[].name` и т.д.
на верхнем уровне). Но реальный бэкенд
(`shifts.service.ts#getZReport`) всегда возвращал **вложенную**
структуру: `shift.{staffName, openedAt, closedAt}`,
`sales.{cashTotal, cardTotal, debtTotal, total, count}`,
`returns.{count, total}`, `cashDrawer.{opening, cashSales,
cashReturns, withdrawals, expected, actual, difference}`, а поля
`duration` в ответе backend вообще нет. Из-за этого `json['staffName']
as String` получал `null` и парсинг падал с `TypeError` при **любом**
реальном ответе — экран Z-отчёта, судя по всему, никогда не работал
против настоящего API. Особенно коварно то, что собственный тест
`z_report_test.dart` и фикстура в
`shift_remote_datasource_test.dart` тоже были написаны под ту же
неверную плоскую структуру — набор тестов, специально посвящённый
Z-отчёту, не мог поймать эту находку в принципе.

**Серьёзность:** критическая — ключевая функция (сверка кассы при
закрытии смены) не работала полностью, при этом ошибка маскировалась
под "непонятный сбой" без намёка на реальную причину.

**Исправлено:** коммит `467751c`
(`fix(mobile): Z-report always failed to parse the real backend
response`). `fromJson` переписан на чтение правильных вложенных
путей, `topProducts` перемаплены на ключи `name`/`quantity`/`total`,
которые уже ожидает `z_report_page.dart`; `duration` теперь считается
на клиенте из `closedAt.difference(openedAt)`. Оба теста
(`z_report_test.dart`, `shift_remote_datasource_test.dart`)
переписаны под реальную вложенную структуру ответа. Проверено
break-then-fix: откат `z_report.dart` воспроизводит именно ту же
ошибку `type 'Null' is not a subtype of type 'String'`, что видна
живьём; весь набор тестов модуля Смены (86 тестов) зелёный с фиксом.

**Подтверждено живьём на эмуляторе** (2026-09-21): открыта и закрыта
смена (начальная сумма 500, закрывающая 600) → Z-отчёт открылся
корректно — показаны ФИО кассира, время смены, длительность "0ч 7м",
разделы "Продажи"/"Возвраты"/"Касса" с реальными нулевыми суммами
продаж и начальной суммой 500.00 TJS, ожидаемая касса 500.00 TJS.

### 🔴 КРИТИЧНАЯ находка (ИСПРАВЛЕНО): калькулятор закята пустеет после возврата из "Настройки закята"

**Как воспроизвести:** "Калькулятор закята" → иконка настроек →
"Настройки закята" → нажать "Обновить" рядом с полем "Курс золота" →
системная кнопка "Назад".

**Фактическое поведение:** экран "Калькулятор закята" возвращался
полностью пустым (только шапка с заголовком и иконками, никакого
контента) — зависало в таком состоянии постоянно, не самоустранялось.

**Корневая причина (подтверждено чтением кода — тот же класс
архитектурной проблемы, что уже встречался и был исправлен в этом
прогоне для Сотрудников/Долгов/Зарплаты):** `ZakatBloc` — общий
экземпляр для `ZakatCalculatorPage` и `ZakatSettingsPage`/
`ZakatHistoryPage`. Переход через голый `context.push(...)` оставлял
страницу калькулятора смонтированной под настройками; кнопка
"Обновить" на экране настроек диспатчит `ZakatSettingsRequested`,
переводя общий `ZakatBloc` в состояние `ZakatSettingsLoaded`. Билдер
калькулятора (`BlocConsumer<ZakatBloc, ZakatState>`) распознаёт только
`ZakatLoading`/`ZakatCalculated`, для любого другого состояния
(включая `ZakatSettingsLoaded`) проваливается в `return const
SizedBox.shrink()` — то есть возврат с экрана настроек **гарантированно**
пустил экран калькулятора, а не только в редком гоночном случае.

**Исправлено:** коммит `f6dc516`
(`fix(mobile): zakat calculator went blank on return from
settings/history`). Переходы на "Настройки" и "Историю" обёрнуты в
`_openSettings`/`_openHistory`, которые `await`-ят `context.push(...)`
и переотправляют `ZakatCalculateRequested` при возврате — по тому же
паттерну, что уже применён для Сотрудников/Долгов/Зарплаты. Добавлен
тест `zakat_calculator_reload_test.dart` с настоящим `GoRouter`.
Проверено break-then-fix; весь набор тестов модуля Закят (11 тестов)
зелёный.

**Подтверждено живьём на эмуляторе** (2026-09-21): "Настройки закята" →
"Обновить" → "Назад" → калькулятор корректно показывает расчёт (850
TJS активов), вместо пустого экрана.

**Примечание по методике:** этот баг — уже **шестой** случай той же
архитектурной проблемы (общий Bloc между списком/деталями или
расчётом/настройками без перезапроса при возврате), найденный и
исправленный в этом прогоне (после Долгов, Сотрудников×2, Зарплаты,
Закята). Стоит запланировать отдельный сквозной аудит всех пар
"список/детали" и "экран/настройки" в приложении на этот паттерн,
а не продолжать находить их по одному в ходе линейного прохода по
плану.
