## Methodology
- Routes extracted with `grep -oE 'Mapped \{/api[^,]+, [A-Z]+\}'` from the live Nest startup log.
- Each route classified into one of: GET (read auth + read no-auth + cross-store), POST/PUT/DELETE empty-body (validation), and where safe a CRUD cycle.
- Mutating endpoints invoked only when (a) easily reversible, (b) clearly disposable, or (c) known to validate-and-reject empty input.
- Skipped per instructions: `DELETE /api/auth/logout`, `PUT /api/admin/subscriptions/:id/approve-payment/:paymentId`, `POST /api/stores` (would create extra store), `POST /shifts/open` with valid body (would change POS state), file-upload endpoints (`/products/import`, `/subscription/upload-receipt`).

## Recommendations

1. **Tighten validation on settings-style PUT/POST** that currently accept `{}` and silently reset/create defaults:
   - `PUT /api/stores/:storeId/receipt-template`
   - `POST /api/stores/:storeId/zakat/settings`
   Add `@IsNotEmptyObject()` on the body DTO, or split into a separate `/reset` endpoint with explicit semantics.

2. **Confirm currencies auth scope.** If exchange rates are intentionally public (mobile app fetches before login), document this in the OpenAPI/README. Otherwise, attach `@UseGuards(JwtAuthGuard)` to `CurrenciesController`.

3. **Localization consistency.** Auth validation messages mix Russian (`Неверный формат номера телефона`) and English (`phone must be a string`) in the same `message[]` array. Either fully localize or fully Anglicize at the API layer; the client can localize codes.

4. **Stable error contract.** All errors observed share `{statusCode, message, timestamp, path}` — good. Keep the `message` type stable: most validators return `string[]`, but business-rule rejections (login, refund) return `string`. Consider always wrapping in `string[]`.

## Notes on coverage limits

- File-upload endpoints (`/products/import`, `/products/import/preview`, `/subscription/upload-receipt`) tested only with the JSON path. Multipart upload not exercised — would need real .xlsx and image fixtures.
- Excluded by policy: `DELETE /api/auth/logout`, `PUT /api/admin/subscriptions/:id/approve-payment`, `POST /api/stores`.
- POS state-changing endpoints (`POST /shifts/open`, `POST /sales`, `POST /sales/:id/refund`, `POST /payroll/.../pay-all`, etc.) tested only with empty bodies for validation behaviour. End-to-end "happy path" (open shift → checkout → close → z-report) not run because rolling back an opened shift requires either an admin-only "force-close" flow or seed-DB reset.
