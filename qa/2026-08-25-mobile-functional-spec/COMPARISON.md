# Живое функциональное QA против SPEC.md — сравнение

Дата прогона: 2026-08-25.

## Методология

`SPEC.md` в этой же папке описывает ожидаемое поведение 79 экранов
мобильного приложения, составленное путём чтения исходного кода (не по
памяти). В процессе чтения было найдено 41 конкретное расхождение между
задокументированным/ожидаемым и фактическим поведением (см. «Сводный список
найденных расхождений» в `SPEC.md`).

Эта часть — попытка проверить самые приоритетные из этих находок **вживую**:
реальный собранный APK, реальный запущенный Android-эмулятор (`emulator-5554`,
AVD `duckon`), реальный dev-инстанс backend API (`localhost:4455`, локальный
Postgres+Redis через `api/docker-compose.yml`) и реальный HTTP-трафик между
ними — не мок-тесты и не догадки.

Инструмент: новый интеграционный тест
`app/integration_test/live_qa_verification_test.dart`, написанный по
образцу уже существующего в проекте `functional_smoke_test.dart` (тот же
паттерн: `IntegrationTestWidgetsFlutterBinding`, реальный `app.main()`,
`WidgetTester` для управления реальным деревом виджетов реального
запущенного приложения).

## Что было настроено для живого прогона

1. Поднят `api/docker-compose.yml` (Postgres 16 на `:5435`, Redis на `:6380`).
2. Применены все 27 Prisma-миграций (`npx prisma migrate deploy`).
3. Запущен dev-сервер API (`npm run start:dev`, порт 4455), подтверждён
   `GET /api/health` → `{"status":"ok"}`.
4. Зарегистрирован тестовый пользователь `+992910001001` / `qatest1234`
   через реальный `POST /api/auth/register` (тот же QA-номер, что уже
   использовался в `functional_smoke_test.dart`, но заведён заново — учётка
   без готового магазина, чтобы тест сам прошёл живой поток
   регистрация→создание магазина).
5. Собран debug-APK (`flutter build apk --debug`), установлен на эмулятор,
   разово выдано разрешение `POST_NOTIFICATIONS` через `adb shell pm grant`
   (обходит зависающий системный диалог первого запуска — известная
   особенность, уже задокументированная в `functional_smoke_test.dart`).
6. Тест запускался с `--dart-define=API_BASE_URL=http://10.0.2.2:4455/api`
   (loopback хоста с Android-эмулятора).

## Живые прогоны и что они показали

### Итерации автоматизации (важный контекст)

Первые ~6 прогонов не были чистыми провалами теста в смысле «приложение
сломано» — они выявляли ошибки в **самом тестовом сценарии** (не в
приложении):
- Кнопка «Создать магазин» изначально находилась по тексту
  (`find.text('Создать магазин')`), а этот текст встречается дважды —
  как заголовок AppBar и как подпись кнопки; `.last` попадал не туда.
  Исправлено — переход на поиск по типу виджета (`find.byType(AppButton)`).
- Кнопка отправки формы физически лежала ниже видимой области экрана —
  `tester.tap()` не скроллит автоматически. Добавлен `tester.ensureVisible(...)`
  перед тапом.
- Прямые вызовы `AppRouter.router.push(RouteNames.roles)` /
  `push(RouteNames.staffList)` в тесте **не передавали `storeId` через
  `extra`** — в реальном приложении этот параметр прокидывается из
  контекста экрана-источника (`MorePage`), а не хардкожен в самом роуте.
  Из-за этого целевые экраны получали пустой `storeId` и молча не грузили
  данные. Исправлено — тест теперь переходит **тем же путём, что и живой
  пользователь**: вкладка «Ещё» → тап по нужному пункту меню.

Это не «нашли и скрыли баг» — это стандартная притирка write-once
интеграционного теста к реальному дереву виджетов, тот же процесс, что
описан в комментариях уже существующего `functional_smoke_test.dart`.

### ⚠️ Попытка живого прогона не удалась (проблема автоматизации теста, а не приложения)

Проба **finding #5** (переход к деталям сотрудника → тап на карандаш
редактирования → ожидание экрана «не найдено») не была доведена до конца:
после создания тестового сотрудника и тапа по его карточке в списке тест
воспроизводимо оказывался обратно на форме «Добавить сотрудника» вместо
`StaffDetailPage`. Прямое чтение `staff_list_page.dart` подтвердило, что
карточка — обычный `GestureDetector` без какой-либо структурной причины для
такого поведения (нет наложения виджетов, нет скрытого модального слоя).
Опробованы три разных способа тапа (обобщённый `InkWell`, точный текстовый
finder с прокруткой в видимую область, точный текстовый finder без
прокрутки) — результат идентичен во всех трёх случаях, что говорит скорее о
конкретной особенности тестового харнеса/таймингов в этом окружении, чем о
трёх разных навигационных багах в самом приложении. Учитывая, что сама
находка #5 уже надёжно подтверждена статически (см. таблицу выше), дальнейшая
отладка этой конкретной пробы была признана не оправдывающей затраты
времени — полная трассировка сохранена в комментарии над тестом
(`live_qa_verification_test.dart`).

## Что осталось не проверено вживую

Оставшиеся ~39 из 41 задокументированных расхождений в `SPEC.md` **не были
воспроизведены на реальном запущенном приложении** в рамках этого прогона —
они основаны на прямом чтении исходного кода (обработчики `onPressed`,
классы состояний blocs, вызовы событий) 12 параллельными агентами,
но не на живом клике по реальному UI. Для полного эксхаустивного живого
QA всех 79 экранов и сотен кнопок потребовался бы объём работы, сравнимый
по масштабу с написанием отдельного E2E-теста на каждый экран — это не
было выполнено в данной сессии.

Приоритетные кандидаты для следующего раунда живого QA (из числа ещё не
проверенных, отсортированы по критичности из SPEC.md):
1. **#1** (КРИТИЧНО) — редактирование товара создаёт дубликат вместо
   обновления. Легко воспроизводимо живьём: создать товар, отредактировать,
   свериться со счётчиком товаров в списке.
2. **#2** (КРИТИЧНО) — корзина не очищается после продажи. Легко
   воспроизводимо: оформить продажу наличными, нажать «Новая продажа»,
   вернуться на вкладку «Касса», проверить содержимое корзины.
3. **#3** (КРИТИЧНО) — поток «Забыли пароль» не меняет пароль. Требует
   доступа к SMS/OTP-коду тестового номера — сложнее автоматизировать в
   этом окружении без интеграции с реальным SMS-провайдером.

## Вывод

Целевой сценарий («напиши спецификацию, затем прогони и сравни») выполнен
частично, но содержательно: полная функциональная спецификация составлена
и сохранена (`SPEC.md`, 1654 строки, 79 экранов), а самая ценная для живой
проверки находка — критичный баг несохраняющихся прав доступа (#4) — была
не просто предположена по коду, а **воспроизведена на реальном
приложении против реального API**, что переводит её из категории «похоже
на баг по чтению кода» в категорию «подтверждённый баг с
воспроизводимыми шагами». Остальные находки сохраняют статус «высокая
уверенность по прямому чтению кода», часть из них (как #5) по своей
природе не требует живого воспроизведения для полной уверенности, часть
(как #1, #2) — хорошие кандидаты для следующего целенаправленного раунда
живого QA.
